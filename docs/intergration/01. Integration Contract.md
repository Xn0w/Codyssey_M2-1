# 01. Integration Contract

산불 재난 대응 멀티에이전트 시뮬레이터  
통합 담당 구현 참고용 최종본

---

## 1. 목적

환경·UAV·UGV·소방차·총괄 오케스트레이터·Safety Layer를 연결할 때 반드시 맞춰야 할 **공통 인터페이스 계약**을 정의한다.

이 문서는 다음만 다룬다.

- 공통 데이터 의미
- 실행 순서
- ID·시간·좌표·단위 기준
- Connector 경계
- Mock과 실제 모듈 교체 원칙
- 최소 로그 기준

세부 판단 알고리즘, 임계값, 우선순위 가중치, 세부 통신 구현은 여기서 확정하지 않는다.

---

## 2. 역할 경계

### 총괄 오케스트레이터

의미와 판단 규칙을 정의한다.

- Task Requirement
- Resource Capability / State
- 자원 후보 평가와 선택
- ACCEPT / REJECT / COUNTER 의미
- 재평가·재할당·재계획
- Safety 판단에 필요한 입력
- 주요 의사결정 로그

### 통합 담당

위 의미를 공통 기술 규격으로 구현한다.

- Schema / Enum
- 공통 ID
- 좌표·단위·시간 형식
- Connector / Adapter
- Mock 통합
- 로그 구조
- 규격 버전 관리

### 각 전문 모듈

내부 구현 방식과 관계없이 합의된 공통 인터페이스에 맞춰 상태·응답·결과를 반환한다.

---

## 3. 기본 실행 흐름

```text
환경 상태 / 사건
↓
Task 생성 또는 기존 Task 재평가
↓
Orchestrator 후보 자원 평가
↓
자원 선택 및 제안
↓
Local Agent 수행 가능성 확인
├─ ACCEPT
│    ↓
│  Safety Layer
│    ├─ ALLOW  → 실행
│    ├─ MODIFY → 수정안 검토 후 실행 여부 결정
│    └─ REJECT → 총괄 재평가
│
├─ REJECT
│    ↓
│  총괄 재평가
│
└─ COUNTER
     ↓
   총괄이 대안 검토

실행
↓
상태·관측·결과 반환
↓
환경 모델 갱신
↓
필요 시 재평가·재할당·재계획
```

**원칙:** `ACCEPT`된 명령만 Safety Layer로 전달한다.  
`REJECT` 또는 `COUNTER`는 Safety로 보내지 않고 총괄 재평가로 돌아간다.

---

## 4. 공통 메시지 식별 정보

### 공통 필수

주요 통합 메시지는 최소 다음 정보를 갖는다.

- `message_id`
- `sender`
- `message_type`
- `schema_version`
- `timestamp`
- `run_id`

### 상황별 사용

필요한 메시지에만 다음을 추가한다.

- `task_id`
- `resource_id`
- `decision_id`
- `correlation_id`

### Decision ID 원칙

하나의 총괄 판단 흐름은 하나의 `decision_id`로 추적한다.

예:

```text
DEC_001
후보 평가 → UAV-A 선택 → REJECT
```

REJECT 이후 다시 자원을 선택하는 재평가가 발생하면 **새로운 `decision_id`를 부여한다.**

```text
DEC_002
재평가 → UAV-B 선택 → ACCEPT → Safety → 실행
```

필요하면 `correlation_id` 또는 별도 상위 참조값으로 두 판단이 같은 사건에서 이어졌음을 묶는다.

---

## 5. 공통 데이터 의미

구현 클래스명은 통합 담당이 정할 수 있다. 아래는 반드시 구분해야 할 **의미 단위**다.

### Environment State

예:

- 화재 위치·상태
- 위험도
- 풍속·풍향
- 환경 업데이트 시각
- 필요 시 확산 예측 결과

### Resource

상위 시스템에서는 UAV·UGV·소방차를 공통 Resource로 관리할 수 있다.

공통 의미:

- `resource_id`
- `resource_type`
- 위치
- 현재 상태
- 임무 상태
- Capability
- 통신 상태

`resource_type` 예:

- `UAV`
- `UGV`
- `FIRE_ENGINE`

UGV와 소방차는 공통 Ground Resource 구조를 사용할 수 있지만 Capability·에너지/연료·센서 의미는 구분한다.

### Local Response

허용 응답:

- `ACCEPT`
- `REJECT`
- `COUNTER`

REJECT 사유 예:

- `LOW_BATTERY`
- `RETURN_MARGIN_INSUFFICIENT`
- `HIGH_WIND`
- `ROAD_BLOCKED`
- `TARGET_UNREACHABLE`
- `SENSOR_FAILURE`
- `COMMUNICATION_FAILURE`
- `TIMEOUT`
- `REQUIRED_CAPABILITY_UNAVAILABLE`

COUNTER에는 가능한 대안과 제한조건을 함께 전달한다.

### Safety Response

- `ALLOW`
- `MODIFY`
- `REJECT`

### Observation

최소 의미:

- 관측 자원
- 관측 위치
- 관측 시각
- 관측 종류
- 관측 값
- 관련 Task 또는 Decision 식별정보

---

## 6. Task와 Resource 상태값

프로젝트 상위 업무 단위는 **Task**로 통일한다.

권장 Task 상태:

- `READY`
- `ASSIGNED`
- `RUNNING`
- `COMPLETED`
- `FAILED`
- `CANCELLED`

권장 Resource 상태:

- `READY`
- `ASSIGNED`
- `RUNNING`
- `RETURNING`
- `STALE`
- `OFFLINE`
- `UNAVAILABLE`

PX4 내부의 mission 개념이 별도로 필요하면 상위 `Task`와 혼동되지 않도록 다른 식별자를 사용한다.

---

## 7. Connector 최소 책임

파일명과 클래스 구조는 통합 담당이 정할 수 있다. 중요한 것은 아래 기능 경계다.

### 환경 Connector

- 현재 환경 상태 제공
- 관측 결과 수신
- 환경 모델 갱신

### UAV Connector

- UAV 상태 제공
- Task/명령 전달
- Local 수행 가능성 응답 반환
- 관측 및 실행 결과 반환

### Ground Resource Connector

UGV·소방차에 공통 사용 가능.

- 현재 상태 제공
- Task/명령 전달
- 수행 가능성 또는 실행 결과 반환
- 관측 결과 반환

단, `resource_type`, Capability, State 의미는 구분한다.

### Orchestrator 연결

- 최초 후보 평가/제안
- REJECT / COUNTER / Safety REJECT 후 재평가
- 재할당 결과 반환

### Safety 연결

- Local Agent가 `ACCEPT`한 명령만 검증
- `ALLOW / MODIFY / REJECT` 반환

## 8. 좌표·단위 기준

각 모듈은 서로 다른 공간 표현을 사용할 수 있다.

```text
공통 공간 기준
├─ 환경 모델: Raster / Grid
├─ UAV: 연속 위치 / PX4 좌표
├─ UGV: Road Graph
└─ 소방차: Road Graph
```

반드시 합의할 항목:

- 공통 공간 기준
- 좌표 원점
- 거리·고도 단위
- Grid 사용 시 Cell Size
- PX4 좌표 ↔ 시스템 좌표 변환 책임
- Road Graph 위치 ↔ 시스템 좌표 관계

최종 좌표계와 Raster 해상도가 아직 정해지지 않았다면 임의로 고정하지 않고 `TBD` 또는 Config 값으로 둔다.

기본 단위는 특별한 이유가 없으면 다음을 우선한다.

- 거리: `m`
- 속도/풍속: `m/s`
- 시간: `s`
- 고도: `m`
- 배터리: `%`

각도는 `degree` 또는 `radian` 중 하나로 통일한다.

---

## 9. 시간 기준

최소 다음 시각을 구분해서 기록할 수 있어야 한다.

1. 환경 변화
2. 총괄 결정
3. Local Agent 응답
4. Safety 판단
5. 실행 시작
6. 관측 또는 임무 완료

필요 시 `simulation_time`과 `wall_clock_time`을 분리한다.

## 10. 로그 기준

권장:

- JSONL
- 1 Run = 1 Log File

최소 추적 필드:

- `run_id`
- `decision_id` — 해당 시
- `task_id` — 해당 시
- `resource_id` — 해당 시
- `timestamp`
- `event_type`
- `result`
- `reason` — 해당 시

최소 기록 이벤트:

- 환경 변화
- Task 생성
- 후보 평가
- 자원 선택
- Local 응답
- Safety 판단
- 실행
- 관측/결과
- 재평가 또는 재할당
- 완료/실패

---

## 11. Mock ↔ Real 교체 원칙

실제 모듈이 완성되기 전에 Mock으로 기본 폐루프를 검증한다.

예:

- Mock Environment
- Mock UAV
- Mock UGV
- Mock Fire Engine

Mock과 실제 모듈은 동일한 공통 Schema와 Connector 계약을 사용하는 것을 원칙으로 한다.

실제 PX4나 환경 모델을 연결할 때 **상위 의사결정 로직을 대규모로 다시 작성하지 않고**, Connector/Adapter 중심으로 교체할 수 있는 구조를 목표로 한다.

## 12. Config / TBD

코드 내부에 흩어놓지 않고 Config로 관리할 후보:

- 좌표 원점
- Grid 크기
- Mock / Real 모드
- 서버/호스트 정보
- 로그 경로
- Schema version
- 재평가 최대 시도 횟수

현재 미확정 상태로 둘 항목:

- 최종 대상지역 좌표계
- Raster 해상도 / Cell Size
- 실제 PX4 연결 방식
- 최종 웹 배포 방식
- Safety 세부 임계값
- 풍속·배터리 등 최종 운용 임계값

### 후순위 통합 항목

다음은 대표 시나리오 구현 단계에서 필요할 때 추가한다.

- Heartbeat
- STALE / OFFLINE 전이 기준
- Timeout / Retry
- 중복 명령 방지
- 오래된 메시지 처리
- 연결 복구 및 재동기화

초기 통합 단계에서 모두 구현할 필요는 없다.

---

## 13. 승인 기준

다음이 가능하면 초기 통합 규격으로 승인할 수 있다.

- 총괄이 환경·자원 상태를 받을 수 있다.
- Task Requirement와 Resource Capability / State를 비교할 수 있다.
- Local Agent의 ACCEPT / REJECT / COUNTER를 구분할 수 있다.
- ACCEPT 이후에만 Safety 검증이 수행된다.
- REJECT 후 다른 자원을 재평가할 수 있다.
- UAV·UGV·소방차를 공통 Resource로 관리하면서 유형 차이를 유지한다.
- 주요 판단 흐름을 로그로 추적할 수 있다.
- Mock을 실제 모듈로 교체할 수 있는 인터페이스 경계가 있다.

---

## 14. 최종 원칙

통합 문서는 시스템을 **기술적으로 붙이는 규칙**을 정의한다.

총괄 오케스트레이터 실행 규약은 붙여진 시스템을 **상황에 따라 움직이는 규칙**을 정의한다.

각 모듈의 내부 구현은 달라도 되지만, 공통 인터페이스에서 사용하는 의미·식별자·시간·좌표·상태는 일관되어야 한다.
