## 발견한 결함과 수정

**팀 `tools/twin_clock.py` 에 'LLM 응답 중 시계 멈춤' 이 없었다.**
- 총괄은 LLM 계획을 기다리는 동안 `/health` 의 `llm.in_flight` 를 1 로 보낸다. 개인 저장소 ADAIR 의 시계는 이 값을 보고 진행을 멈추지만(사용자 결정 2026-10-08), 팀 저장소 시계에는 이 부분이 빠져 있었다.
- 그래서 100배속에서 LLM 응답 약 23 s 동안 시뮬레이션이 약 39분(sim 540 → 2880 s) 흘렀다. 그사이 규칙 지시서가 자원·구역을 차지해 첫 계획이 `OBS_PLAN_DISCARDED NO_ASSIGNMENT_VALID_NOW` 로 버려졌다 (원인: `BLOCK_NO_LONGER_SELECTABLE`, `RESOURCE_NO_LONGER_AVAILABLE`).
- 수정: ADAIR 의 `_wait_llm` 과 `--orch`·`--no-llm-pause` 옵션을 그대로 옮겼다. 총괄이 응답하지 않으면 멈추지 않고 진행한다. 멈춘 시간은 배속 기준 시각에서 뺀다.

## 남은 한계 (시험으로 확인 안 됨)

- 시계를 멈춰도 `input_changed_during_call=True` 는 계속 나온다. mock 드론·UGV 는 실제 시각으로 움직이고, 총괄은 LLM 을 기다리는 동안에도 규칙 지시서(HEAD 추종)를 계속 내보내므로(`engine.py` `_call_while_dispatching_orders`) 배정이 빠진다. 팀 수정 후 실행에서 통째 8건·일부 4건, 개인 저장소 ADAIR 같은 구성 실행(logs/twin/20261017_083651)에서도 첫 계획 배정 3건 중 2건이 통째로, 넷째 계획 일부가 빠졌다.
- UAV 운용 상당 부분은 여전히 규칙(HEAD 추종·`RULE_AFTER_CHARGE`)이 정한다. 수정 전 실행 sim 14700·20100 계획은 드론 2대가 가용인데 UGV 에만 배정했다.
- 이번 실행에서 타는 칸이 0~1칸뿐이라 계획 품질을 평가하기에는 확산 정보가 빈약하다.
- 규칙 대체·시간 초과·잘못된 계획(repair) 경로는 실제 호출로 확인하지 않았다 (가짜 모델 단위 시험만 있음).
- `test_live_llm.py` 는 예전 `propose()`(우선순위 묶음) 경로만 부른다. 트윈이 쓰는 `plan_observations()` 실호출 시험은 없다.

## 발견한 결함: 기상 측정(ENV_SENSE/WEATHER) 무한 재출동 — 수정함

**증상.** sim 27480 s 에 첫 기상 임무가 생긴 뒤, 소방차 A-fire1 이 (첫 출동 sim 56460 s, 반복은 61260 s 부터) 기상 재측정 임무 3건을 끝없이 돌았다: 출동 → 즉시 도착 → 측정 → `OBSERVATION_REQUIREMENT_NOT_MET` 재오픈 → 같은 자원 재출동. 시나리오 중 재오픈 18회, 시계가 멈춘 뒤에는 약 3초마다 1회 재출동(약 2분간 40회)했다. UGV(A-ugv1·B-ugv1)도 같은 임무에서 실패했다. 시계 수정과는 무관한 기존 동작이다.

**원인.** 지상 자원이 멈춘 도로 지점이 목표 칸 밖(약 200 m)이라 기상 측정의 `target_covered` 가 false 다(`observation.py` simulate_weather 는 도착 위치가 목표 칸 안인지만 본다). `_conclude` 는 재오픈만 하고, 다음 배정은 직선거리 순이라 이미 그 자리에 있는 같은 자원(ETA 0)을 다시 고른다. 실패한 자원을 임무 단위로 기억하는 장치가 없었다.

**수정 (`orchestrator/engine.py` `_prior_uncovered`).** ENV_SENSE + WEATHER 임무에 한해, 그 임무의 이전 시도 중 측정은 했지만(`result != FAILED`) 목표 칸을 못 덮은 자원을 장부(`list_attempts` + `get_observation(aid, "MAIN")`)에서 뽑아 기존 `filter_candidates(excluded=...)` 로 넘긴다 (`_dispatch`, `_candidate_ids`).
- 완료(COMPLETED) 의미는 그대로 — 못 덮은 측정은 여전히 재오픈된다.
- 제외는 그 임무 안에서만, 자원 종류와 무관 (UAV 포함). 다른 임무에서는 정상 후보.
- 다른 후보(UAV 등)가 있으면 그쪽으로 넘어가고, 없으면 기존 `NO_FEASIBLE_CANDIDATE` → HOLD(`NEW_RESOURCE_OR_INPUT`). 새 자원이 가용해지면 다시 평가하되 실패한 자원은 계속 제외 (장부에서 다시 계산하므로 재시작 뒤에도 같다).
- 새 상태·협상 구조 없음.

**검증.**
- 시험 추가 (`test_uav_unavailable_ugv_fallback.py`): 같은 임무 재송신 없음 + HOLD(`NEW_RESOURCE_OR_INPUT`) + 제외 사유 기록 / HOLD 뒤 드론 가용 시 드론으로 인계 / 다른 임무에서는 같은 UGV 정상 후보. 기존 `test_ugv_stopping_far_from_target_does_not_complete` 단언은 그대로. 수정을 빼면 새 시험이 실패한다.
- 전체 pytest: 588 passed · 8 skipped · 0 failed (어제 기준선 585 + 새 시험 3).
- 결함 재현 장부(094745) 사본 재생: 세 임무에서 A-fire1·A-ugv1·B-ugv1 이 정확히 제외, 다른 종류 임무는 영향 없음.
- 수정 후 트윈 전체 2회 (logs/twin/20261017_111022, 20261017_120848): FAULTED·UNKNOWN·예약 누수·중복 execute 0, 소방차 HOME 0, UGV 귀소 20 / 23건, LLM 25 / 24회 채택·규칙 대체 0·폐기 1 / 0, 시계 멈춤·재개 25/25 · 24/24. 시나리오 종료 뒤 마무리(약 10~20 s) 다음 60 s 동안 장부 증가 0 (수정 전에는 계속 증가).
- 코드 리뷰·결과 대조: 별도 Opus 검증 에이전트 승인.

**미확인 (남은 것).**
- 수정 후 트윈 2회 모두 기상 측정 임무가 생기지 않았다 (재측정 요청이 이미 열린 정찰에 붙음, LLM 판단에 따라 sim 720 s 부터 흐름이 갈림). 그래서 **고친 경로가 트윈에서 실시간으로 실행된 것은 아직 확인하지 못했다.** 근거는 단위 시험과 결함 장부 재생이다.
- 실패 자원이 다 빠진 뒤 남는 후보가 멀리 있는 소방차(B-fire1, 약 18 km)일 수 있다. 출동해도 칸 밖이면 한 번 실패 뒤 제외되어 반복은 자원 수로 묶이지만, 18 km 출동이 운용상 바람직한지는 따로 판단이 필요하다.
- 측정 결과가 FAILED(환경이 기상값을 주지 않음)인 경우는 자원 탓이 아니므로 제외하지 않는다 — 그 경로의 반복은 이번 수정 범위 밖이다.
- SNAPSHOT_CHANGED 거절 실행당 약 760~820건(816 시나리오 중 · 763 · 761)은 기존 known issue (재평가 뒤 정상 진행, 차단 사례 없음) — 이번 수정 대상 아님.
