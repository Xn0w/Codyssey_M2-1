현재 스크립트 문제 [확인, `ugv/tools/px4-stop.sh`]:
- 6~10행: pid 파일의 PID 에 `kill` 한 번 → **대기·생존 확인 없이 즉시 `rm -f`**. PID 재사용 검사 없음.

설계:

1. **기동 측 기록** (`px4-start.sh`): gz 서버·PX4 를 `setsid nohup …` 으로 띄워 각자 프로세스 그룹을 갖게 하고, `$STATE_DIR/run/<RUN_ID>/procs.json` 에 `{role, pid, pgid, starttime(/proc/<pid>/stat 22번째 필드), cmdline, world, GZ_PARTITION, instance}` 기록. 기존 `*.pid` 파일은 호환용으로 유지. `RUN_ID` 는 `ADAIR_RUN_ID` 환경변수(chain 이 TAG 전달), 없으면 시각. gz 런처(ruby)가 서버를 **같은 프로세스**에서 돌리는지 자식을 두는지 [추정] → 첫 실행에서 `pstree -p <pid>` 로 확인해 메타에 남기고, 어느 쪽이든 **pgid 단위**로 신호를 보낸다.
2. **종료 절차** (`px4-stop.sh`): manifest 의 각 항목에 대해 ① `/proc/<pid>` 존재 + starttime 일치 + cmdline 에 기대 토큰(`gz sim`/`px4 -i N`) 포함 → 아니면 "PID 재사용/이미 종료" 로 기록하고 **신호 보내지 않음** ② `kill -TERM -<pgid>` ③ 0.2 s 간격으로 최대 `STOP_GRACE_S`(기본 10 s) 생존 확인 ④ 생존자 `kill -KILL -<pgid>` ⑤ 3 s 내 소멸 확인 ⑥ 모두 확인된 뒤에만 manifest 를 `procs.done.json`(결과 포함) 으로 이동. **확인 전 PID 정보 삭제 금지**.
3. **소유권 확인 후 잔존 검사**: `pgrep -u $USER -f 'gz sim'` 각 PID 의 `/proc/<pid>/environ` 에서 `GZ_PARTITION` 을 읽어 우리 파티션(`adair_ugv`)·우리 월드 이름이면 "잔존(우리 것)"; 다른 파티션이면 **보고만** 하고 죽이지 않음. 이어 `gz service -l` 에 `/world/<WORLD>/…` 가 남아 있으면 1 s 간격 3회 재확인(discovery 캐시 지연 고려) 후 잔존으로 판정.
4. **결과 코드**: 0 깨끗함 / 2 우리 잔존(실행 오염) / 3 manifest 없음(`--legacy` 를 줄 때만 기존 패턴 kill 수행, 아니면 아무 것도 죽이지 않음). 출력은 JSON 한 줄(`logs/ugv/stage4/stop_<TAG>.json` 로 복사).
5. **기동 측 거부**: `world_up` 이 참이면 `GZ_REUSE_WORLD=1` 이 아닌 한 **중단**하고 `CONTAMINATED` 를 출력·결과 코드 6. PX4 인스턴스 재사용도 같은 규칙.
6. **chain 측**: `run_sc_v2.sh` 후속판(`run_sc_v3.sh`, chain56 종료 후 작성)이 stop 결과 코드 2·기동 결과 6 을 받으면 `logs/ugv/stage4/<TAG>.contaminated` 를 쓰고 그 회차를 **무효(오염)** 로 분류, 체인은 다음 회차로 진행하되 보고서에 횟수 명시. "다른 Gazebo 가 떠 있다" 만으로 기존 결과를 무효화하지 않는다(파티션이 다르면 보고만).

단위 시험(P0, WSL, Gazebo 없이): 별도 `STATE_DIR=/tmp/adair-stop-test` 에서 `setsid sleep 1000` 류 더미를 manifest 에 등록하고 ① TERM 무시 더미(`trap '' TERM`) 가 KILL 로 끝나는지 ② 이미 끝난 PID 와 같은 번호를 다시 쓰는 재사용 시나리오(starttime 불일치)에서 신호를 보내지 않는지 ③ 결과 코드 0/2/3 을 확인. 실제 Gazebo 는 P1 첫 회차 기동·종료 때 `pstree`·`gz service -l` 로 확인.

## 5. 조향·구동 개선은 조건부 (지시서 5절)

### 5.1 필요 판정 기준 (P2 결과로 판단, 둘 중 하나라도 충족할 때만 후보 제작)

- **아커만 후보 필요**: 어떤 교차로에서 susp 후보 3회 중 2회 이상 ① |조향 실제각| ≥ 15° 구간 1 s 이상에서 측정 yaw rate / 요구 yaw rate < 0.7 이고 ② 앞 두 바퀴의 접선력 `ft` 가 차체 좌표 횡방향에서 **부호 반대**이거나 내측 바퀴가 포화(`ft ≥ 0.9·μ·fn`, μ=1.0 [확인 SDF 96행]) 인데 외측은 아닐 때.
- **바퀴 속도 분배 후보 필요**: 회전 중 구동 바퀴 관절속도와 기하 요구 속도(`detail_report` 의 기하요구, 후축 중심 ICR) 차가 10 % 넘고 좌우 바퀴 종방향 접선력 부호가 반대(한쪽이 제동)일 때.

### 5.2 기하 (SDF 실측 [확인] 축간 2.7, 윤거 1.6)

PX4 는 자전거 모델 조향각 δ 하나를 servo_0 으로 보낸다(`RA_WHEEL_BASE 2.7`, `RA_MAX_STR_ANG 0.5236`, `SIM_GZ_SV_MAXA1 30` [확인, airframe 24~26, 68~69행]; servo_0 단위 rad [확인, SDF 7행 주석] — PX4 서보 출력이 정규화값을 ±30° 로 바꿔 rad 로 내보내는지는 [추정], 첫 계측에서 steer_l 과 ULog `normalized_steering_setpoint` 비로 확인). 후축 중심 회전반경 R = L/tan δ, 내·외측각 δ_i = atan(L/(R − t/2)), δ_o = atan(L/(R + t/2)).

| δ(명령) | R | δ_i | δ_o |
|---|---|---|---|
| 10° | 15.3 m | 10.5° | 9.5° |
| 20° | 7.42 m | 22.2° | 18.2° |
| 30° | 4.68 m | **34.8°** | 26.2° |

내측각이 관절 한계 30°(`0.5236`, SDF 177행)를 넘는다. 처리: ① 두 조향 관절 한계를 ±35°(0.6109) 로 올리고 PX4 `RA_MAX_STR_ANG` 는 유지(R_min 4.7 m 보존, `profiles.py` r_min 불변) 또는 ② δ 를 δ_i ≤ 30° 가 되도록 포화(δ ≤ 26.2°, R_min 5.5 m 로 커져 계획 도구와 불일치) → ①을 기본. 0 부근은 선형(δ_i ≈ δ_o ≈ δ), 좌우 대칭은 부호만 뒤집고 안쪽 판정을 δ 부호로.

구현 선택지:
| 방식 | 평가 |
|---|---|
| gz-sim `AckermannSteering` 시스템 | cmd_vel 입력으로 관절을 **직접 구동** → 기존 JointController/JointPositionController 와 중복, PX4 actuator 경로 우회 → **채택 불가** |
| Python gz.transport 브리지(servo_0 → servo_0_l/r, motor_speed → 바퀴별) | 별도 프로세스·지연 추가. **시험 후보 전용**, 운영 금지 |
| 소형 C++ gz system plugin `AckermannSplit`(WSL, gz-sim8 헤더로 빌드) | servo_0 구독 → 두 조향 관절 목표각 각각 발행(기존 JointPositionController 는 토픽만 `servo_0_l/r` 로 바꿔 유지). PX4 인터페이스 보존. 운영 가능. 약 0.5 일 |

바퀴 속도 분배: 각 바퀴 접지점 속도 = |v_center + ω × r_wheel| / R_w (직진에서는 동일, 회전에서 차이 허용). "이상적 분배" 라고만 부르고 기계식 차동장치 재현이라 쓰지 않음. 구현도 같은 플러그인에서 actuator 0 을 바퀴별 속도로 분배.

### 7.2 빠진 것

- **진행 방향 오류** 감지가 없다(OFF_ROUTE 는 거리만, STALLED 는 60 s). 반대 방향으로 되돌아가는 동안 거리가 작으면 감지가 늦다.
- **이탈 위험 예측**(정지거리 안에서 차체가 도로 띠를 벗어날 것인가)이 없다 — OFF_ROAD 는 벗어난 뒤 확인.
- 남은 위험으로 기록된 "첫 이탈 0.7~3.4 m 는 막지 못함"(단계1·2 결과 18행) 은 차량 개조(서스펜션)가 맡는 부분이고 안전 기능의 몫이 아님 — 집계를 섞지 않음.
- 건너뛰기의 "도로 내 연결·회전 가능성" 확인은 `pass_allowed` 에 없음(방향·차체 안만) → 지시서 7.3 에 따라 **별도 검증 항목**으로 두고 P4 에서는 PASS_SKIP=0 유지.

### 7.3 최소 수정안과 순서

1. **P4-A (수정 없이 차량 효과만)**: 96회 매트릭스 조건(`STALL_DETECT=0 PASS_SKIP=0`) 결과가 그대로 차량 효과. 이 때 실패 회차의 "고장 뒤 추가 이탈·정지거리·정지 후 재이동" 은 `failure_timeline.py` 로 산출해 기록(안전 기능 없이).
2. **P4-B (안전 기능만 추가)**: 같은 후보·같은 조건에서 `UGV_PX4_STALL_DETECT=1`(PASS_SKIP=0, OFFROAD_STOP=straight 기본) 로 문제 7곳 × D8 × 3회 + 정상 대조 9곳 × D8 × 1회 = 30회(≈55 min). 지표: MISSION_STALL 발생 시각 − 경유점 최근접 시각(감지 지연), 고장 뒤 추가 이탈 m, 정지거리, 재이동, 정상 대조 오감지 수. **안전 정지 성공은 임무 성공으로 집계하지 않음**(judge3 `arrived` 는 그대로 거짓).
3. **P4-C (조건부 최소 추가, P4-B 에서 감지 지연 > 2 s 또는 추가 이탈 > 2 m 사례가 있을 때만)**: `ugv/vehicle.py` 경로 이탈 블록(1081행 앞) 에 **진행 방향 오류** 감지 `OFF_HEADING_DEG=90, OFF_HEADING_S=2.0` (속도 ≥ 1 m/s 이고 경로선과의 거리 ≥ 2 m 일 때만, 경로 접선 vs heading) 추가 → `_fail("OFF_HEADING")`+`_safe_stop`. 단위 시험 `test_fault_stop.py` 에 2건(정상 U자 경로 오감지 없음, 역주행 2 s 감지). wt_fix 새 커밋. 3 m 반경·NAV_ACC_RAD·도로 폭·마찰 변경 금지.
4. **P4-D 재시험**: 회전 중 취소(`--second`), 반대 방향 새 목표, 같은 도로 뒤쪽 목표, 막다른 길, 통신 단절(`_test/link` 훅, `link_loss_compare.py`) — 기존 기준 그대로 각 1~2회(≈12회, 25 min). 의도적 경유점 놓침 유도 = base 모델 + D8 j494943(자연 재현, 3/3 실패 [확인 chain53]) 3회로 고장 뒤 지표 기록.
